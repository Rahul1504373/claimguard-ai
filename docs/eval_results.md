# ClaimGuard AI — Agent Evaluation Results

**Status: Partial eval.** This covers the three deterministic agents
(Pattern, Statistical, Retrieval/RAG) and the risk-scoring formula only. It
does **not** evaluate the two Gemini-backed agents (Extraction, Consistency)
— see "What's not covered" below for exactly why, and what it would take to
close that gap.

Generated by `scripts/run_eval.py`, run against the 42 labeled claims in
`claimguard_synthetic_claims.json`. Every number below is computed directly
by that script — nothing here is estimated or assumed.

Run on 2026-10-04, `python3 scripts/run_eval.py` (re-run after adding the

## What's actually being tested

For each of the 42 claims, in claim-ID order (CG-001 first, matching how a
real submission stream would arrive):
1. Run the real `pattern_agent.run()` — repeat-claimant, shared-address-ring,
   duplicate-submission, policy-date-anomaly, claim-frequency-spike checks —
   against everything already processed so far.
2. Run the real `statistical_agent.run()` — Benford's Law + Isolation Forest
   — against the growing claim pool.
3. Run the real `retrieval_agent.run()` — TF-IDF narrative similarity search
   (RAG) against everything already processed so far, raising a
   `similar_to_flagged_claim` signal when this claim closely resembles a
   PAST claim that this same eval run already computed as flagged.
4. Run the real `explainability_agent.compute_deterministic_score()` — the
   exact same scoring function production uses — to get a `risk_tier`.
5. Save the computed status before moving to the next claim, exactly like
   the real pipeline, so step 3's "was it flagged?" check for later claims
   reflects genuinely computed history — never the dataset's ground-truth
   labels leaking into the comparison.
6. Compare `risk_tier in (moderate, high)` against the dataset's own
   `intended_flag` ground truth (`"none"` = should stay clean; anything else
   = should be flagged).

This is the genuine, server-side-verified scoring path from Fix #2 — the
same arithmetic that decides `claim["status"]` in production.

## What the Retrieval Agent (RAG) actually added to this result

Short, honest answer: **no change to the headline numbers** (still 89.2%
accuracy / 100% precision / 69.2% recall) on this particular 42-claim
dataset. Exactly one claim (CG-036) triggered a `similar_to_flagged_claim`
signal — and it was already correctly flagged by `shared_address_ring`
pattern matching anyway, so retrieval added corroborating evidence, not a
different outcome, here.

This is not a sign the Retrieval Agent doesn't work — the live, real-time
test during development (two claims submitted back to back with
paraphrased-but-matching narratives) confirmed it correctly detects a 73%
narrative-similarity match and raises the flag exactly as designed. It's a
property of this specific dataset: these 42 claims were purpose-built to
test the *other* fraud-pattern types (exact duplicates, shared addresses,
frequency spikes, policy-date anomalies) — none of them is a "reworded
resubmission with different wording but the same story," which is
precisely the gap `duplicate_submission`'s exact-text match would miss and
retrieval-based similarity is meant to catch. Stated honestly rather than
inflating this eval's apparent coverage: this dataset doesn't currently
contain a case that isolates the Retrieval Agent's unique value, so this
number doesn't demonstrate it, even though the live test does.

## What's NOT covered, and why

The Extraction Agent and Consistency Agent (the two Gemini multimodal
stages) are **not evaluated here**, for two concrete, unavoidable reasons:

1. **MOCK_MODE returns one fixed canned response for every claim**, no
   matter what's actually submitted (see `app/agents/extraction_agent.py` /
   `consistency_agent.py` — `MOCK_RESPONSE` is a hardcoded constant). Running
   42 different claims through the mocked pipeline would produce 42
   *identical* extraction/consistency outputs — scoring that against 42
   different ground truths would be a meaningless number, not a real eval.
2. **The dataset's photo fields are placeholder filenames**, not real image
   files (documented in `claimguard_dataset_methodology.md`). Even with a
   real `GEMINI_API_KEY`, there's no actual image for Gemini's vision input
   to analyze.

So this harness measures exactly what can honestly be measured for free
right now: the two deterministic agents and the score arithmetic, using the
dataset's own ground-truth `incident_date`/`claimed_amount` fields as a
stand-in for "assume extraction already succeeded." The 5 claims whose
*only* intended signal is a pure photo-vs-narrative mismatch (CG-025 to
CG-029 — these need Gemini vision, not pattern logic) are reported as
**out of scope**, not folded into the accuracy number as failures — missing
them here reflects a gap in what this harness can test, not a defect in the
Pattern/Statistical agents, whose job was never to catch that signal class.

**To close this gap for real:** run the actual pipeline with a real
`GEMINI_API_KEY` and a matching/mismatching photo for each of the 42 claims,
then run this same comparison against `intended_flag`. That's a legitimate
next step, genuinely buildable, but it is a different piece of work (it
needs real images and will consume live API quota, even if small) from what
this harness does today.

## Why precision is 100% (0 false positives)

None of the 24 deliberately-clean claims (including CG-011/CG-001-024, the
high-value-but-fully-documented claim included specifically to test
amount-bias) were ever wrongly flagged. Worth noting honestly: Benford's
Law nonconformity fires on a large share of claims in this 42-row sample
(expected — Benford's Law needs a much larger, more naturally-distributed
sample than 42 hand-constructed claims to be statistically meaningful; see
`statistical_agent.py`'s own `BENFORD_MIN_SAMPLES = 30` comment, "ideally
100+"). But a Benford flag alone is worth +15 points, below the 30-point
"moderate" threshold — so it never, by itself, triggers a false flag. It
only matters once combined with an actual pattern flag. This dataset's
sample size is at the edge of what Benford's Law's own documented minimum
allows, so take the Benford-specific signal as illustrative, not
statistically robust, until tested on a much larger claim volume.

## Why these 4 misses happened (and why they're not really "misses")

CG-031, CG-032, CG-037, CG-038 are the **1st and 2nd claims** in two
3-claim fraud-pattern sequences (repeat-claimant and claim-frequency-spike,
respectively). `pattern_agent.py`'s thresholds (`REPEAT_CLAIMANT_THRESHOLD
= 2`, `FREQUENCY_THRESHOLD = 2`) require at least 2 *other* claims already
on file before a pattern is confirmed — by definition, you cannot detect "3
claims in 45 days" on the first or second claim alone; the signal only
exists once the third occurrence arrives. CG-033 and CG-039 (the 3rd claim
in each sequence) are correctly flagged. This is accumulation-dependent
detection behaving as designed, not a bug — but it's a real, worth-stating
limitation: **this system catches a pattern on the claim that completes it,
not the ones that precede it.** A production deployment would want a
lower-confidence "early warning" signal for claims 1-2 of a sequence, which
is a genuine improvement idea for a future iteration, not something to
claim as already built.
